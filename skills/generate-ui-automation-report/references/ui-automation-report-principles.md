# UI 自动化测试报告原则

## 目标

UI 自动化报告首先服务评审和缺陷定位，不服务展示脚本运行过程。读者打开报告后，应先得到测试结论、失败影响和风险，再按需展开单条用例证据。

## 信息架构

1. 首页优先展示结论、范围、统计、失败影响和风险。
2. 用例执行明细按失败优先排序，但展开状态不作为固定规则。
3. 通过用例只需要展示摘要、断言数量和截图数量；只有复核时才展开。
4. 缺陷聚合必须展示失败断言、关联需求/用例和证据路径。
5. HTML 正文不再额外展示重复的概览表，避免和用例执行明细重复。

## 证据链

每条用例必须能追溯到：

1. 用例 ID。
2. 测试标题。
3. 关联需求或来源用例。
4. 执行步骤。
5. 通过标准。
6. 断言明细。
7. 截图证据。

每条断言必须能说明：

1. 检查项是什么。
2. 期望是什么。
3. 实际是什么。
4. 结果为什么通过或失败。
5. 证据截图在哪里。

## 截图规则

1. 截图是证据，不是报告主内容。
2. 默认只展示缩略图和截图名称。
3. 点击缩略图时应在报告内弹窗预览，避免读者跳离当前用例上下文。
4. 弹窗中提供原图链接用于复核。
5. 不允许让大图占据首屏或挤压统计、失败影响、用例概览。
6. 对抽屉、弹窗、表格区域优先截取业务主体区域，避免无意义遮罩占比过高。

## 外部质量门禁

以下情况不得标记为正式交付通过：

1. 只有 `passed`，没有检查项、期望和实际。
2. 测试标题缺失或只写页面名。
3. 失败用例没有失败断言。
4. 失败断言没有实际结果。
5. 截图链接不存在。
6. 用例明细默认占用过大，导致报告不能扫读。
7. 首页缺少失败影响或上线建议。
8. 报告里出现真实 token、cookie、密码、密钥或连接串。

质量门禁是产物治理信息，不是业务测试结论。HTML 报告正文不展示质量门禁摘要或明细；完整结构化结果写入 `report-self-check.json`，供交付前核验、排查报告生成器、CI 或审计时使用。
