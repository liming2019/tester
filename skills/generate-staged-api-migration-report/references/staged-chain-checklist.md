# 两阶段迁移报告补充检查

## 何时读取

仅在以下场景再读取本文件：

- 输入材料不完整，但需要判断能否降级为 `draft`
- “核验范围与口径” 和 “核验时间证据” 被混写
- 差异样例字段不足，只剩自由文本摘要
- 多接口报告需要决定主报告和分接口页怎么拆
- 覆盖缺口、`N/A` 和真实差异容易混淆

本文件只补充边界处理，不重复主 Skill 的主流程。

## 易混概念

### 核验范围与口径

这里只放筛选条件和核验口径，例如：

- 核验对象
- 核验类型
- 时间筛选范围
- 批次范围
- 环境
- 对象数量

### 核验时间证据

这里只放执行后看到的实际证据，例如：

- 报告生成时间
- 批次执行窗口
- 源时间字段实际范围
- 目标时间字段实际范围

不要把“上传时间范围”写进时间证据，也不要把“源 createTime 实际范围”写成筛选条件。

## 三类内容必须分开

报告里至少要有三类独立信息：

1. `字段赋值规则`
   说明理论上应该怎么迁。
2. `字段准确性核验结果`
   说明实际上有没有迁对。
3. `覆盖缺口与不适用说明`
   说明这次为什么没法充分判断，或为什么字段本身不适合做值一致性核验。

不要把这三类内容混在同一张表里。

## 什么时候只能降级为 draft

出现以下任一情况时，不要硬生成“正式通过”的主报告：

- 缺少字段赋值基线
- 缺少字段准确性核验结果
- 关键接口、关键字段或关键文件没有直接证据
- 只有 Markdown 摘要，没有可复用 JSON
- 多接口场景下连接口清单都无法确认

这类情况优先：

1. 输出结构化阻塞说明
2. 总体结论使用 `BLOCKED` 或 `WARN`
3. 明确写出缺失输入，而不是脑补

## 覆盖缺口的正确写法

以下情况统一进入 `覆盖缺口与不适用说明`：

- 未做目标层反向全量扫表
- 仅能通过批次参数间接证明筛选范围
- 没有对象存储直接证据
- 没有文件任务表或状态证据
- 只按映射命中链路确认，未做反向覆盖
- 字段完全由目标系统生成
- 字段只用于追溯，不参与业务判定

状态只允许：

- `WARN`
- `BLOCKED`
- `N/A`

不要把这些内容写成：

- `0 条差异`
- `正常通过`
- `未发现问题`

## 差异样例最少字段

差异样例至少保留以下字段：

- `business_key`
- `source_id`
- `staging_id`
- `staging_evidence`
- `target_id`
- `difference_type`
- `difference_field`
- `source_value`
- `target_value`
- `difference_note`

如果当前只能拿到摘要级材料：

1. 先把能确定的字段拆出来
2. 缺失字段明确写“未展开”或“缺少直接证据”
3. 如关键字段整体缺失，移入 `覆盖缺口与不适用说明`

不要再退化成一整块自由文本。

## 多接口报告拆分原则

多接口场景下：

- 主报告只给执行结果概述、核验明细、核验结论概述，不平铺所有字段差异
- 每个接口单独生成 HTML 明细页
- JSON 明细继续保留为结构化证据

主报告至少先回答：

1. 总体结论是什么
2. 测试接口数、通过接口数、阻塞接口数、失败接口数分别是多少
3. 每个接口的名称、路径、范围、规则、环境和状态是什么
4. 每个接口的明细页应该点哪里
5. 每个接口的核验结论概述是什么

接口页再回答：

1. 这个接口的字段规则
2. 这个接口的字段核验结果
3. 这个接口的代表差异样例
4. 这个接口自己的结论

## 常见误判

- 把 `N/A` 字段误判为 `FAIL`
- 把覆盖不足误写成“0 条差异”
- 把一致率高的零容忍字段直接放行
- 把字段覆盖总结写成失败清单
- 把 Markdown 草稿当成正式 HTML 报告

## 人工补写时的顺序

如果脚本生成后仍需人工补写，保持以下顺序：

1. 执行结果概述
   展示总体结论、测试接口数、通过接口数、阻塞接口数、失败接口数
2. 核验明细
   用接口索引表展示接口名称、核验接口路径、核验范围、核验规则、核验环境、核验状态、查看明细
3. 核验结论概述
   一个接口一块，块内展示接口名称、核验接口路径、核验结果概述；不要使用项目符号列表

补写完成后，重新跑输出校验，不要直接交付。
