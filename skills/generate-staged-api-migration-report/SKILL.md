# 两阶段迁移核验报告规范

使用本 Skill 时，只负责把“已经核验出来的结果”整理成统一报告，不负责执行核验动作本身。

也就是说：

- 负责：报告结构、章节编排、差异分组、样例展示、结论口径、失败原因总结、脱敏、UTF-8 自检。
- 不负责：查库、调接口、跑比对、算差异、判定映射关系、核查对象存储、补数据。

## 适用场景

当任务满足以下条件时使用本 Skill：

1. 迁移链路属于 `源/第三方接口 -> 中间表/映射表/快照表 -> 目标业务表`。
2. 已经有核验结果，例如总量统计、差异清单、重复数据、字段覆盖说明、文件检查结果、阻塞项。
3. 当前目标是“生成或统一一份迁移核验报告”，而不是继续做数据核验。

如果项目配置 `reporting.default_generate_report=true`，且上游核验 Skill 已完成结构化结果产出，则即使用户没有单独再说“请出报告”，也应继续生成报告；只有用户明确说“不生成报告”时才跳过。

以下情况不要使用本 Skill：

- 还没有核验结果，想让 Codex 先去执行核验。
- 需要输出 SQL、接口请求、对象存储探查脚本、核验逻辑方案。
- 只是想设计核验用例或核验流程。

## 输入要求

生成报告前，至少确认已具备以下输入；缺项时不能脑补，只能输出模板、占位说明或 `BLOCKED` 结论：

1. 核验范围与口径：迁移对象、核验类型、业务模块、批次范围、环境范围、时间筛选口径。
2. 核验时间证据：报告生成时间、批次执行窗口、源时间字段实际范围、目标时间字段实际范围。
3. 三层说明：源基线来源、中间层来源、目标层来源。
4. 业务键与 ID 映射说明。
5. 阶段一结果：源 -> 中间层 的统计或差异结论。
6. 阶段二结果：中间层 -> 目标层 的统计或差异结论。
7. 全链路结果：源标识、中间层标识、目标标识的一致性结论。
8. 差异样例：缺失、重复、字段差异、关系差异、文件差异等代表样例。
9. 字段覆盖说明：哪些字段仅存在中间层、哪些字段不落库、哪些字段为默认值或系统生成。
10. 结论草稿或结论口径：PASS/WARN/FAIL/BLOCKED。
11. 阻塞项与前提限制。

## 推荐上游产物

如果上游使用 `verify-api-migration-result` 执行核验，优先消费它输出的结构化产物：

1. `reports/details/<任务名>_api_migration_verification.json`
2. `reports/details/<任务名>_api_migration_verification.md`

其中 JSON 是主输入，Markdown 是辅助明细。优先从 JSON 读取：

- `verification_scope`
- `time_evidence`
- `source_baseline`
- `staging_layer`
- `target_sources`
- `business_keys`
- `source_to_staging_summary`
- `staging_to_target_summary`
- `full_chain_consistency_summary`
- `uniqueness_summary`
- `field_differences`
- `relationship_differences`
- `file_differences`
- `field_coverage`
- `coverage_gaps`
- `conclusion`
- `blocked_items`

## 报告生成流程

按以下顺序组织报告，不要跳步：

1. 先统一术语：源基线、中间层、目标层、批次、重跑、字段覆盖、差异样例。
2. 再按“两阶段链路”组织结果，而不是按零散字段堆砌。
3. 先写摘要和结论，再写差异明细。
4. 先写分组汇总，再放 1 到 3 个代表样例。
5. 生成 HTML 后按 UTF-8 重新读取，确认中文无乱码。

## 核验范围与时间拆分规则

报告中必须明确区分两类时间信息：

1. `核验范围与口径` 中的时间
这是筛选条件或核验口径的一部分，例如：
- 上传时间范围
- 批次筛选范围
- 仅核验某个时间区间内的数据
- 核验类型：全量 / 抽样 / 两阶段迁移核验

2. `核验时间证据` 中的时间
这是核验后观察到的实际时间证据，例如：
- 报告生成时间
- 批次执行窗口
- 源 `createTime` 实际范围
- 目标 `create_time` 实际范围

不要把“筛选条件时间”和“实际时间分布”混在同一张表里。

## 覆盖缺口展示规则

如果某个维度没有被独立核验、没有做全量反扫、没有直接证据，或只能间接证明，不能把它写成“0 条差异”或“正常通过”。

这类内容必须统一放入 `覆盖缺口与范围限制` 章节，并显式标记为：

- `WARN`：已有部分证据，但覆盖不完整
- `BLOCKED`：缺少直接证据，无法形成有效判断

典型场景包括：

- `目标有中间层无` 未做独立全量扫表
- 上传时间范围只能通过批次参数间接证明
- 缺少目标开放接口、对象存储或文件任务证据
- 某些维度仅按映射命中链路判断，未做反向覆盖

不要把这类信息和真正的 `0 条差异` 混放在同一张结果表里。

## 强制章节

报告至少包含以下章节：

1. 核验范围与口径
2. 核验时间证据
3. 源基准来源
4. 中间层来源与目标来源
5. 批次与重跑口径说明
6. 业务键与 ID 映射说明
7. 阶段一采集核验结果
8. 阶段二落库核验结果
9. 全链路一致性核验结果
10. 唯一性与重复数据核验结果
11. 覆盖缺口与范围限制
12. 字段覆盖总结
13. 源有中间层无 / 中间层有源无
14. 中间层有目标无 / 目标有中间层无
15. 字段值差异表
16. 关系差异表
17. 文件可用性差异表
18. 概述/总结
19. 结论
20. 失败原因总结

如果某章节没有差异：

- 保留该章节的汇总结果。
- 可以省略该章节的详细样例表。

## 展示顺序规则

主报告的阅读顺序必须是：

1. 先让读者看懂链路和范围。
2. 再让读者看懂阶段一、阶段二和全链路结果。
3. 再让读者知道有哪些维度没有被完整覆盖。
4. 再展示字段覆盖这种“解释型信息”。
5. 最后再放差异样例和失败原因。

不要一上来就平铺所有差异记录。

## 差异分组规则

差异明细必须按“差异类型”或“差异字段”分组展示，默认每组只放 1 到 3 个代表样例。

每条样例至少保留：

- 业务键
- 源标识
- 中间层标识
- 中间层证据
- 目标标识
- 差异字段或差异类型
- 源值
- 目标值
- 差异说明

`中间层证据` 必须优先展示真正有诊断价值的内容，例如：

- `extra_json.createTime=...`
- `view_migration_file_task: 不存在`
- `file_task.status=PENDING`
- `job_param.uploadStartTime=...`

不要只是重复 `old_id -> new_id` 这种已经在“中间层标识”里出现过的映射链；如果只有映射链而没有快照证据，必须明确写成“仅有映射标识，缺少中间层直接证据”。

如果是文件类差异，再额外展示：

- 源 URL
- 中间层 URL 或路径
- 目标 URL 或路径
- 文件大小
- 时长

## 字段覆盖总结规则

字段覆盖总结用于解释“为什么有些字段不参与直接差异判定”，而不是把它们误报成迁移失败。

统一使用以下分类：

1. `中间层有但未配置落业务表`
2. `仅存中间层用于追溯`
3. `业务表无中间层来源-NULL`
4. `业务表无中间层来源-默认值`
5. `业务表无中间层来源-空串`
6. `业务表无中间层来源-系统生成或混合规则`

字段覆盖总结应放在报告靠前位置，先于大段差异明细。

## 结论口径

报告结论统一使用以下口径：

- `PASS`：主链路、关键字段、关键关系、关键文件结果均满足要求，且无关键阻塞项。
- `WARN`：存在可解释差异、覆盖提示或非关键缺口，但不影响主链路判断。
- `FAIL`：关键记录缺失、关键字段错误、关系断裂、关键文件不可用、重复污染等问题成立。
- `BLOCKED`：缺少源基线、批次范围、映射说明、核验结果或必要前提，无法形成有效结论。

不要因为样例数量少就直接写 `PASS`；必须与已有核验结论一致。

## 失败原因总结规则

失败原因总结只负责“整理已有原因”，不负责推理新的核验逻辑。

优先按以下方向归类：

1. 阶段一采集不完整
2. 阶段二落库不完整
3. 全链路 ID 断裂
4. 重跑或补跑导致重复
5. 关系链不一致
6. 文件路径或对象存储结果异常
7. 字段覆盖范围与预期不一致
8. 关键前提缺失导致结论阻塞

## 自检要求

交付前必须自检：

1. 主结论、摘要、分章节结论是否一致。
2. 是否误把“字段覆盖说明”写成“迁移失败”。
3. 是否把明细堆得过长，影响阅读。
4. 是否泄露真实 token、cookie、密码、连接串、对象存储密钥。
5. HTML 按 UTF-8 读取后是否存在乱码、`????`、编码污染。

## 输出要求

最终回复用户时，至少给出：

1. 简短结论
2. 报告路径
3. 使用的结论口径（PASS/WARN/FAIL/BLOCKED）
4. 是否存在必须研发修复的问题
5. 是否存在因输入不足导致的阻塞项
