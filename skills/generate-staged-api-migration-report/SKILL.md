# 两阶段迁移报告生成

兼容说明：新任务默认使用 `generate-api-migration-report` 并设置 `chain_type=staged`。本 Skill 暂时保留为历史 staged 专用入口；后续主报告样式和公共规则以 `generate-api-migration-report` 为准。

本 Skill 负责把“已经完成的两阶段迁移核验结果”整理成正式交付物，不负责重新执行核验。

职责边界：

- 负责：读取结构化核验结果、确定交付分层、生成主 HTML/单接口明细 HTML/分接口 HTML/JSON 明细、把多接口主报告做成简洁总览导航页、统一结论口径、标记覆盖缺口、脱敏、交付前校验。
- 不负责：查库、调接口、重新跑比对、补业务规则、替调用方决定要不要出报告。

## 先用现成资产

- `scripts/validate_staged_report.py`
  先校验输入契约，再校验输出文件。
- `scripts/render_staged_report.py`
  优先用脚本生成主 HTML、分接口 HTML 和 JSON 明细，减少自由发挥。
- `assets/report_contract.json`
  硬约束、枚举、章节清单、最小字段要求的唯一来源。
- `assets/report_template.html`
  主报告和分接口页共用模板。
- `references/staged-chain-checklist.md`
  只在遇到边界场景、易混概念或样例不足时再读。

## 适用前提

仅在以下条件同时满足时使用：

1. 迁移链路是 `源/第三方接口 -> 中间层 -> 目标层`。
2. 已经完成核验，当前任务是生成或统一报告。
3. 调用方已经决定“本次需要出报告”。

不要在本 Skill 内部再根据项目配置推断是否要生成报告。上游执行迁移测试/API 迁移核验后默认调用本 Skill 生成 HTML 报告；只有用户明确不需要测试包报告、不生成报告或不生成 HTML 时，上游才跳过报告生成。

## 首选输入

优先消费 `verify-api-migration-result` 的结构化结果：

1. `reports/details/<任务名>_api_migration_verification.json`
2. `reports/details/<任务名>_api_migration_verification.md`

关键顶层字段以 `assets/report_contract.json` 为准。标准模式至少应包含：

- `verification_scope`
- `time_evidence`
- `source_baseline`
- `staging_layer`
- `target_sources`
- `business_keys`
- `source_to_staging_summary`
- `staging_to_target_summary`
- `full_chain_consistency_summary`
- `conclusion`
- `blocked_items`

字段级输入优先读取：

- `source_field_inventory`
- `field_rule_coverage_summary`
- `unmapped_source_fields`
- `interface_inventory`
- `field_assignment_rules`
- `field_accuracy_summary`
- `field_accuracy_details`
- `field_validation_coverage`
- `field_coverage`
- `coverage_gaps`

如果用户额外提供映射文档、配置表、代码规则、PRD 或接口文档，可以补进结构化输入；不要直接跳过字段章节。

## 交付分层

按以下模式交付：

- `draft`
  仅输出结构化 JSON 和阻塞说明。只在用户明确要求“仅草稿/仅结构化数据”或关键输入不足时使用。
- `standard`
  仅用于单接口。输出单接口明细 HTML + JSON 明细，不生成主报告，也不生成分接口目录。
- `full`
  仅用于多接口。输出主 HTML + JSON 明细 + 分接口 HTML 明细页。多接口场景下必须使用，除非用户明确说不需要 HTML 正式报告。

只有一个接口时，正式 HTML 指单接口明细报告；只有多个接口时，正式 HTML 才包含主报告。只有 `JSON` 或 `Markdown` 不能宣称已完成正式报告。

## 固定执行流程

1. 先把上游结果整理成一份 canonical JSON；必要时保留原始 JSON，不要直接在自由文本上拼报告。
2. 运行 `scripts/validate_staged_report.py input` 校验输入契约。
3. 根据接口数量确定 `draft / standard / full`：单接口固定为 `standard` 明细报告，多接口固定为 `full` 主报告加分接口明细页。
4. 优先运行 `scripts/render_staged_report.py` 生成 HTML 和 JSON 明细。
5. 只有脚本覆盖不到的特殊章节，才允许人工补写；补写后仍需满足 contract 中的章节顺序和枚举口径。
6. 运行 `scripts/validate_staged_report.py output` 校验输出文件、章节、UTF-8、分层以及页面是否存在横向溢出；优先通过加宽内容区、换行和列宽优化解决，必要时允许表格局部横向滚动兜底，但不允许页面级横向溢出。
7. 校验不过则回到上一步修正，不要带着未校验结果交付。

## 主报告固定结构

只有核验多个接口时才输出主报告，主报告固定使用以下 3 段结构：

1. 执行结果概述
   必须展示总体结论、测试接口数、通过接口数、阻塞接口数、失败接口数。
2. 核验明细
   这里不是字段明细表，而是接口索引区。固定展示接口名称、核验接口路径、核验范围、核验规则、核验环境、核验状态、查看明细。
3. 核验结论概述
   按接口分块展示，每个接口一块，块内展示接口名称、核验接口路径、核验结果概述；不要使用项目符号列表或把多个接口写成一个大段。

主报告只做总览、概述和导航，不承担字段级详表。目标数据库赋值规则及核验结果、差异样例、覆盖说明、源接口字段盘点、源基线和目标来源证据都放到单接口明细 HTML 或分接口 HTML。
主报告不得把 `batch_rows`、请求批次样例、原始 `job_param` 列表或大段嵌套 JSON 直接平铺到正文。

## 必须守住的规则

- `源接口字段清单`、`已纳入规则字段`、`N/A 字段`、`未纳入规则字段` 必须显式展示，不要假设调用方已经做过字段覆盖自检。
- `源基准来源` 必须展示第三方或旧系统实时接口的非敏感关键请求参数，例如 `videoType`、`isInner`、时间范围、分页/分批策略和 `videoIds` 过滤方式；出现“未返回 N 条”“live 覆盖不足”等结论时，不能省略请求过滤条件。
- `源接口字段覆盖自检` 里的“接口名称”应优先展示源接口名称/展示名；接口路径单独放在“接口路径”列，不要把路径误填到名称列。
- `unmapped_source_fields` 只要非空，就不能生成正式主报告；必须返回阻塞或先补规则。
- 分接口页的字段章节必须命名为“目标数据库赋值规则及核验结果”，并把赋值规则与字段准确性核验合并到同一张表中展示。
- `目标数据库赋值规则及核验结果` 只展示目标业务表字段，不展示 `view_migration_*` 迁移映射表、批次表、映射辅助表等中间层表字段。
- `目标数据库赋值规则及核验结果` 必须按目标业务表拆分；每个目标数据库字段一行，即使同一字段在主批注、回复等不同场景来源不同，也要合并在该字段的“赋值规则”单元格中说明，不能把同一个目标字段拆成多行。
- `目标数据库赋值规则及核验结果` 固定列为：`表字段`、`字段名`、`赋值方式`、`预期赋值规则`、`实际核验规则`、`核验级别`、`检查记录数`、`不匹配记录数`、`状态`、`差异说明`。
- `表字段` 列展示数据库技术字段名，例如 `id`、`media_id`；`字段名` 列展示中文业务含义，例如 `批注ID`、`所属素材ID`，不得反向显示。
- `预期赋值规则` 必须说明设计/文档预期从哪里取值、如何生成或查映射、最终写入哪个目标字段；优先使用固定句式：`源接口无对应字段，迁移默认写入固定值：字段=xxx`、`源接口无对应字段，迁移默认写入空值：字段=NULL/空字符串/空JSON`、`源接口无对应字段，迁移写入：字段=迁移程序落库时间/目标系统审计时间`、`源接口预期字段：xxx，写入 yyy`、`源接口预期字段：xxx；关联 <映射表/目标表> 映射取值 yyy`。
- 默认值、系统生成值和审计字段必须写清楚实际值或生成口径，例如固定值 `字段=aaa`、允许为空、迁移执行时间、目标系统当前时间、目标系统审计人；不得只写“写入 create_time”“写入 update_by”这类字段名重复。
- `实际核验规则` 必须说明本次核验实际发现或实际使用的来源字段、映射链路、目标实际模式；如果预期来源是 `aaa`，核验时发现实际使用的是 `bbb`，该列必须展示 `bbb`。不得把该列写成“检查目标字段是否等于某值”这类断言语句；断言和通过标准放到核验级别、状态、差异说明或验收标准中。
- 当结构化结果提供 `expected_assignment_rule`、`actual_validation_rule`、`rule_basis` 或 `rule_consistency_status` 时，分接口页必须拆成 `预期赋值规则` 和 `实际核验规则` 两列展示，不得再合并到一个“赋值规则”单元格；`rule_basis`、`rule_consistency_status` 不单独成列，必须合并进 `状态` 或 `差异说明`，只在 `WARN`、`BLOCKED`、`N/A` 或需要解释风险时展示。
- 如果实际核验使用了接口文档未列字段，例如运行态才出现的嵌套数组、回复列表或扩展字段，报告必须标明该字段是“实际核验依据”或“待确认规则依据”，不能写成接口文档预期规则；关键字段缺少文档或迁移设计依据时，状态必须保留 `WARN` 或 `BLOCKED`，不得为了报告通过改写为 `PASS`。
- `差异说明`：不匹配记录数为 0 时显示“无差异”；存在差异时必须展示差异说明，并优先列出 1-3 条结构化代表样例，每条样例单独换行。
- 除真实源字段名、数据库字段名、接口路径等技术字段外，主报告和分接口页中的自定义标题、字段标签、按钮文案、说明文案默认使用中文。
- 字段列表列在可读性优先的前提下，应优先按“字段名：中文释义”展示；字段较多时允许单元格内纵向滚动，避免把整行无限拉长。
- `目标数据库赋值规则及核验结果` 中的字段、规则和差异说明必须用普通文本列表展示，不要使用胶囊、圆角标签、圆圈包裹等装饰化样式。
- 覆盖不足只能标记为 `WARN`、`BLOCKED` 或 `N/A`，不要伪装成 `0 条差异`。
- `PASS` 不能只凭样例少或一致率高得出；关键字段、关键关系、关键文件、关键前提都要满足。
- 缺少字段赋值基线或字段准确性核验结果时，不得写“字段准确性通过”。
- 主报告只做总览、概述和导航；字段明细落到分接口 HTML，不要把所有接口差异平铺在主报告正文。
- 主报告的接口级状态只允许展示 `PASS`、`BLOCKED`、`FAIL`；`WARN`、`N/A` 等风险或字段级状态只放在明细页解释。
- `核验明细` 区的分接口入口统一使用简短中文入口，例如“查看详情”；不要把长接口名直接塞进按钮文案。
- 如需输出失败或风险原因，只在单接口明细 HTML 或分接口 HTML 中展开；主报告不单独设置“失败原因总结”章节。
- `N/A` 仅用于不适合做值一致性核验的字段，不要误写成失败项或覆盖缺口。
- 零容忍字段以 contract 为准；一旦成立错误，不能仅因一致率较高而放行。

## 总体结论推导

统一使用：

- `PASS`
- `WARN`
- `FAIL`
- `BLOCKED`

推导顺序：

1. 任一核心接口存在 `FAIL`，总体结论为 `FAIL`。
2. 任一零容忍字段存在成立错误且影响业务正确性，相关接口结论为 `FAIL`。
3. 缺少关键规则基线或关键证据，无法判断关键字段是否正确，结论为 `BLOCKED`。
4. 无 `FAIL`，但存在覆盖缺口、抽样限制或非关键差异，结论为 `WARN`。
5. 仅当关键接口、关键字段、关键关系、关键文件都满足要求且无关键阻塞项时，结论才可为 `PASS`。

## 自检重点

- 主结论、摘要、分章节结论是否一致。
- 是否把覆盖说明写成失败。
- 是否只剩 Markdown 草稿而没有正式 HTML。
- HTML 是否能按 UTF-8 重新读取，且不存在乱码或 `????`。
- 页面和主容器是否存在横向溢出；若表格启用了横向滚动，是否仅作为局部兜底而非整页溢出。
- 差异样例是否仍然退化成自由文本块。
- 关键字段是否都能追溯到赋值规则来源。
- 多接口主报告是否能直接回答“整体是否通过、每个接口是什么状态、从哪里进入明细”；单接口报告是否直接展示完整核验明细。

## 最终回复用户

最终回复至少给出：

1. 简短结论。
2. 正式 `HTML` 路径；单接口时说明这是明细报告，多接口时说明这是主报告。
3. 结构化 `JSON` 明细路径。
4. 分接口 HTML 明细页路径或目录；单接口未生成分接口目录时，说明原因是“单接口直接输出明细报告”。
5. 使用的结论口径。
6. 关键字段总数、已有规则基线字段数、已完成准确性核验字段数。
7. `FAIL`、`BLOCKED`、`N/A` 字段数。
8. 是否存在必须研发修复的问题。
9. 是否存在因输入不足导致的阻塞项。

遇到边界场景、术语冲突或样例字段不足时，再读取 `references/staged-chain-checklist.md`。
