# 蓝湖需求提取规范

这份文档是 `lanhu-requirements-extractor` 的配套执行规范。

用途只有一个：

- 把蓝湖需求提取过程固化成**可复用、可校验、可追责**的执行步骤

它不替代 [SKILL.md](C:/Users/Administrator/.codex/skills/lanhu-requirements-extractor/SKILL.md)。
`SKILL.md` 定义“做什么”，本规范定义“具体怎么做，做到什么程度才算完成”。

## 1. 适用范围

适用于以下页面类型：

- Axure 原型页
- 蓝湖嵌入式原型页
- 带右侧“页面说明”的蓝湖产品页
- 有明显交互入口的表格管理页、配置页、详情页、分析页

尤其适用于：

- 存在 `新增` / `编辑` / `删除` / `详情` 按钮
- 存在 `Tab` / 下拉切换 / 热区跳转
- 原型正文、右侧说明、弹窗说明分散在不同位置

## 2. 执行原则

1. 不接受“只抓静态内容”的半完成结果。
2. 不接受“截图里能看到按钮，JSON 里没有交互项”的结果。
3. 不接受“只抓右侧页面说明”的结果。
4. 不接受“页面真实内容在 iframe，但只分析外层蓝湖壳”的结果。
5. 不把版本过滤留给下游测试点或测试用例步骤处理。

## 3. 标准执行顺序

1. 登录蓝湖
2. 打开目标项目、目标文档、目标页面
3. 识别原型承载层
4. 确认目标版本归属
5. 提取静态需求来源
6. 提取交互态需求来源
7. 去重与归类
8. 输出结构化 JSON
9. 执行输出前校验

如果第 3、4、6、9 任一步未完成，不应直接交付最终结果。

## 4. 原型承载层识别

这是第一道强制检查。

每次进入蓝湖页面后，先回答以下问题：

1. 当前看到的是蓝湖外层壳，还是原型本体
2. 原型是否在 `iframe`
3. 原型是否在独立 frame 中，例如 `lan-mapping-iframe`
4. 原型是否为 Axure HTML 页、图片热点页、动态面板页

建议按以下顺序检查：

1. 检查页面 frame 列表
2. 检查 DOM 中的 `iframe`
3. 识别大尺寸原型区域的 `src`
4. 进入对应 frame 再执行后续正文提取和点击操作

常见错误：

- 在蓝湖外层页面找到右侧说明后，误以为已拿到完整需求
- 直接读取 `body.innerText`，但真实可交互内容在内层 frame
- 截图能看见原型页面，自动化却没切到对应 frame

判定规则：

- 如果真实原型在 frame 中，后续提取必须在该 frame 内执行
- 如果未确认承载层，不允许进入“需求提取已完成”状态

## 5. 版本过滤规范

如果用户指定了目标版本，例如 `1.4.6`：

1. 正文区仅保留命中目标版本的内容
2. 混合版本页必须显式标记 `version_match`
3. 混合版本页仅保留与目标版本直接相关的说明
4. 明显属于历史版本、旧逻辑、旧字段的内容必须剔除

建议字段：

- `version_match`
  - `exact`
  - `mixed`
  - `excluded`
- `included_in_target_version`
  - `true`
  - `false`

## 6. 静态需求提取顺序

建议按以下顺序提取：

1. 原型正文结构化说明
2. 画布内注释
3. 画布内说明文案
4. 右侧页面说明
5. 页面截图中的显式字段、表格列、按钮文本

注意：

- 正文结构优先于截图 OCR
- 注释优先读取运行时数据源
- 右侧说明不能替代正文与交互态
- 通用控件名不是优先答案，业务字段名优先

## 7. 交互态覆盖规范

这是第二道强制检查。

只要页面存在以下任一入口，就必须尝试触发：

- `新增`
- `编辑`
- `删除`
- `详情`
- `导出`
- `操作`
- `查看`
- `更多`
- `Tab`
- 下拉切换
- 热区 / hotspot
- 表格操作列

### 7.1 最低覆盖要求

每个页面至少完成：

1. 枚举明显交互入口
2. 至少触发一次每类典型入口
3. 保存触发后的截图
4. 提取标题、字段、按钮、说明文案

### 7.2 交互态记录规则

每条交互态至少包含：

- `trigger`
- `trigger_type`
- `interaction`
- `result_type`
- `title`
- `fields`
- `actions`
- `notes`
- `screenshot`

### 7.3 弹窗类页面特别规则

如果页面是表格管理页、配置页或主列表页：

- `新增` 弹窗必须抓
- `编辑` 弹窗必须抓
- 若存在 `详情`、`删除确认`、`绑定`、`配置` 等次级弹窗，也要抓

如果点击后没有可见变化：

- 允许记录为 `no_visible_change`
- 但必须是在实际点击验证后记录
- 不能用“没时间点”或“看起来不像弹窗”替代验证

## 8. 失败判定清单

出现以下任一情况，提取结果应判定为失败或未完成：

1. 页面截图中有明显交互按钮，但 `interaction_states` 为空
2. 表格管理页存在操作列，但没有任何弹窗、二级页或操作态记录
3. 页面明显在 iframe 中，但只抓了外层蓝湖 DOM
4. 只抓了右侧页面说明，未抓正文或交互态
5. 混合版本页未做目标版本过滤
6. 输出内容与页面截图明显不一致
7. 点击后出现弹窗，但未记录标题、字段或按钮

## 9. 输出前校验清单

在生成最终 `requirements.json` 前，逐项确认：

1. 是否识别并进入了真实原型承载层
2. 是否完成版本过滤
3. 是否提取了正文、注释、说明文案、右侧说明、交互态
4. 若页面存在交互入口，`interaction_states` 是否非空
5. 截图里出现的关键按钮、表格列、弹窗是否都能在结构化结果中找到对应项
6. 是否存在“截图里有弹窗，JSON 里没有弹窗”的情况
7. 是否存在“截图里有新增/编辑，JSON 里无交互项”的情况

如果任一项不通过：

- 继续补抓
- 不要先交付再解释

## 10. 证据保留规范

建议至少保留以下证据：

- 页面原始截图
- 点击前截图
- 点击后截图
- 原始文本抓取结果
- 运行时对象抓取结果
- 结构化输出结果

对关键交互态，建议同时保留：

- 弹窗标题
- 字段清单
- 默认值
- 可选项
- 操作按钮

## 11. 自动化脚本要求

自动化脚本必须满足以下要求：

1. 中文选择器优先使用 UTF-8 或 Unicode 转义
2. 不依赖终端默认编码
3. 文本定位失败时，保留结构定位兜底方案
4. frame 页面必须显式切换，不假设主页面就是原型页面
5. 重要点击步骤必须留截图

推荐做法：

- 文本定位 + class/id 定位双轨并存
- 先探测 frame，再执行点击
- 点击前后都抓取一份页面状态

## 12. 推荐交付结构

推荐输出顺序：

1. `requirements.json`
2. 页面截图
3. 交互态截图
4. 必要时补充 HTML 核验文件

如果需要向下游交付测试点或测试用例：

- 先保证当前 JSON 结构完整
- 不要把缺失交互态的半成品继续传下去

## 13. 最终完成判定

只有同时满足以下条件，才可视为需求提取完成：

1. 页面定位完成
2. 原型承载层确认完成
3. 目标版本过滤完成
4. 五类需求来源提取完成
5. 存在交互入口的页面已完成交互态提取
6. 输出前校验通过
7. `requirements.json` 可直接供下游使用

只满足其中一部分时，应该标记为“部分完成”或“待补抓”，而不是“完成”。
