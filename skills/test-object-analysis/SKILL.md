# 测试对象分析

本 Skill 用于回答“这个需求到底要测哪些对象”。它是测试点和测试用例生成前的前置分析，不替代下游测试点提取或测试用例设计。

## 执行顺序

1. 做需求有效性审查。
2. 识别需求来源和证据等级。
3. 拆测试对象。
4. 为每个对象补充状态、规则、权限、数据关系和风险。
5. 生成对象级测试场景。
6. 标记待确认项和无依据扩展。
7. 输出可交给下游 Skill 的结构化中间产物。

禁止跳过对象分析直接生成测试点或测试用例。若用户已经明确要求生成测试点/测试用例，完成本 Skill 输出后再继续调用下游流程。

## 输入审查

先检查以下信息是否明确：

- 需求目标、版本、业务范围。
- 输入材料类型：PRD、原型、截图、蓝湖结构化需求、接口文档、变更说明、已有测试点或缺陷记录。
- 涉及页面、模块、角色、接口、数据表、外部系统。
- 验收标准、上线范围、回归范围。
- 权限边界、数据边界、环境边界。

如果信息不足，不要阻塞全部工作。拆分为：

- 可立即分析：材料明确支持的测试对象和规则。
- 待确认后分析：缺少依据的业务规则、状态流转、接口参数、权限边界、数据一致性要求。

## 证据等级

输出时必须区分来源，不得把经验补充伪装成需求事实。

| 等级 | 来源 | 处理方式 |
|---|---|---|
| L1 | 原型可见、PRD 明确、蓝湖 Notes 明确、接口文档明确 | 可进入正式测试对象和场景 |
| L2 | 用户补充说明、历史缺陷、项目 AGENT_RULES.md 已验证规则 | 可进入正式测试对象，标注来源 |
| L3 | 资深测试经验推导但材料未明确 | 进入“测试补充/待确认”，不得直接写成正式需求 |
| L4 | 无材料依据的泛化联想 | 不纳入输出，必要时列为不建议纳入范围 |

## 测试对象维度

按以下维度拆解，缺少依据的维度可以省略或标为待确认：

1. 页面与交互对象：页面入口、筛选、表单、列表、弹窗、抽屉、按钮、提示、空状态、加载状态、错误状态。
2. 业务实体对象：用户、账户、订单、广告计划、广告单元、创意、资质、合同、发票、优惠券、审批单等真实业务实体。
3. 状态流转对象：草稿、待审核、审核中、审核拒绝、启用、暂停、冻结、余额不足、已结束、撤回、重试等状态及合法/非法流转。
4. 权限与角色对象：主账号、子账号、代理商、运营、财务、只读角色、跨账户/跨租户访问、旧链接访问、接口鉴权。
5. 数据与一致性对象：前端展示、接口返回、数据库记录、缓存、报表、流水、日志、外部系统同步、历史数据兼容。
6. 外部依赖对象：支付渠道、审核系统、消息通知、对象存储、第三方回调、定时任务、异步同步。
7. 风险对象：并发、重复提交、幂等、越权、状态竞争、部分成功、失败回滚、数据延迟、补偿任务、审计留痕。

当项目属于广告账户、投放平台或磁力金牛类系统时，优先扫描：

- 账户对象：账户类型、账户状态、开户资质、冻结/解冻、主子账号关系。
- 资金对象：余额、充值、退款、授信、消耗、发票、合同、流水一致性。
- 广告对象：计划、单元、创意、预算、出价、定向、审核状态、投放状态。
- 权限对象：主账号、子账号、代理商、运营、财务、只读角色、跨账户访问。
- 报表对象：消耗、转化、指标口径、数据延迟、维度切换、导出一致性。

## 对象分析规则

对每个测试对象至少尝试补充以下信息：

- 对象名称。
- 对象类型。
- 来源证据。
- 关键字段或属性。
- 可执行操作。
- 默认状态和交互后状态。
- 业务规则和边界。
- 权限边界。
- 数据关系和一致性检查点。
- 正常、边界、异常、兼容、权限、数据一致性、回归场景。
- 风险等级：P0/P1/P2/P3。
- 待确认项。

不确定的信息必须写入待确认项。不要用“系统正确处理”“页面正常显示”“按规则处理”这类空泛表述。

## 目标单据字段映射门禁

当需求涉及“源系统 / OA / 中间层创建第三方或目标业务单据”时，必须单独拆出目标单据字段映射对象，不能只把“创建成功”作为主链路覆盖。

至少识别以下内容：

- 目标单据单头字段：申请人、公司、部门、日期、接收人、状态、备注等材料明确出现的字段。
- 目标单据明细字段：商品、资产、数量、金额、编码、序号、分类等材料明确出现的字段。
- 源字段到目标字段的映射关系、映射配置、主数据编码转换和生效口径。
- 拆单、合单、分组、汇总后，每张目标单据的字段归属是否仍对应正确源明细。
- 创建请求字段、回查字段、页面展示字段和本地回写字段之间的一致性。
- 映射缺失、禁用、无权限、多义、缓存过期或主数据漂移时的阻断和异常回写。

如果字段来源或映射确认表缺失，不得省略该测试对象；必须写入待确认项，并在下游输入中保留“按映射确认表逐项核对 / 映射表缺失时阻塞”的测试对象。

## 场景生成规则

围绕对象生成场景，而不是围绕需求原文扩写。

- 正常场景：对象可被创建、查询、修改、提交、审核、启停、导出或同步。
- 边界场景：金额、预算、次数、时间、状态、数量、精度、长度、额度、频率、分页、历史数据。
- 异常场景：接口失败、超时、重复提交、无效输入、外部依赖失败、部分成功、失败回滚。
- 权限场景：入口可见性、前端拦截、接口鉴权、跨账户/跨租户访问、旧链接访问、权限变更即时性。
- 数据一致性场景：页面、接口、数据库、缓存、报表、流水、日志、外部系统是否一致。
- 兼容场景：浏览器、分辨率、历史数据、旧版本链接、不同账号类型或不同投放目标。
- 回归场景：关联模块、存量数据、上下游流程、历史缺陷高发点。

只把 L1/L2 证据支持的内容作为正式场景。L3 内容进入“测试补充/待确认”。

## 输出格式

默认输出一份 Markdown 结果，包含以下章节：

1. 需求审查结论。
2. 测试对象地图。
3. 对象状态与规则矩阵。
4. 权限边界清单。
5. 数据一致性检查点。
6. 风险场景清单。
7. 待确认问题清单。
8. 下游测试点生成输入。
9. 不建议纳入当前范围的无依据扩展。

“下游测试点生成输入”必须放在一个 `plaintext` 代码块中，使用真实 Tab 缩进，便于继续交给 `$extract-functional-test-points` 或测试用例生成流程。

推荐结构：

```plaintext
页面/模块名称
	测试对象：对象名称
		对象类型：业务实体/状态流转/权限/数据一致性/页面交互/外部依赖/风险
		来源证据：L1/L2/L3 + 简要来源
		关键规则
			规则说明
		状态与边界
			状态或边界说明
		权限边界
			角色/入口/接口鉴权说明
		数据一致性
			页面/接口/数据库/缓存/报表/日志一致性说明
		建议生成测试点的场景
			正常场景
			边界场景
			异常场景
			权限场景
			数据一致性场景
		待确认项
			需要产品/研发/业务确认的问题
```

## 下游衔接

当用户要生成测试点：

1. 先输出本 Skill 的测试对象分析。
2. 将“下游测试点生成输入”交给 `$extract-functional-test-points`。
3. 下游只把有明确依据或已标注为测试补充的内容转为测试点。

当用户要生成测试用例：

1. 先输出本 Skill 的测试对象分析。
2. 先生成测试点。
3. 再把高价值测试点落成测试用例。
4. 测试用例必须覆盖正常、边界、异常、兼容、权限、数据一致性和回归影响范围。

当上游是 `$lanhu-to-testcase`：

1. 先由 `$lanhu-requirements-extractor` 提取结构化需求。
2. 将页面级需求摘要交给本 Skill 进行对象分析。
3. 再将本 Skill 的下游输入交给 `$extract-functional-test-points`。

## 禁止事项

- 禁止把测试对象分析直接写成最终测试用例。
- 禁止把无依据经验扩展写成需求事实。
- 禁止为了凑全维度补不存在的对象、状态、接口、数据库表或权限规则。
- 禁止只按页面按钮拆对象，忽略业务实体、状态流转、权限和数据一致性。
- 禁止输出重复对象或多个名称不同但验证点相同的场景。
- 禁止用空泛预期替代可验证结果。

## 自检清单

输出前必须确认：

- 已区分正式需求、测试补充、待确认项和无依据扩展。
- 每个正式测试对象都有来源证据。
- 已覆盖页面/业务/状态/权限/数据/风险中与材料相关的维度。
- 复杂业务已覆盖正常、边界、异常、兼容、权限、数据一致性和回归影响范围。
- 下游测试点生成输入使用 `plaintext` 代码块和真实 Tab 缩进。
- 没有泄露 token、cookie、密码、生产库连接串等敏感信息。
