# 生成 UI 自动化测试用例

使用本 Skill 时，只负责把测试点整理为可评审、可继续脚本化的 UI 自动化测试用例文件，不直接生成 Playwright 脚本。

## 输入前提

至少确认以下信息：

1. 测试点来源文件路径，例如 `testpoints/*.md` 或 XMind 降级 Markdown。
2. 目标范围：版本、页面、模块或功能区；若只做局部页面，必须明确范围。
3. 输出目录；默认优先写入项目 `testcases`。
4. 是否已有定位资产、Page Object 或页面 URL；若已有，只作为映射参考，不要把本 Skill 变成脚本生成流程。

若版本标题、页面名称、功能是否已下线、权限口径或测试数据前置不清晰，先记录到“待确认项”，不要脑补。

## 何时读取参考模板

开始输出最终用例文件前，读取：

- [ui-automation-testcase-template.md](references/ui-automation-testcase-template.md)

只有在需要确认标准章节、表头字段或用例示例时再展开阅读，不要把参考模板全文重复写回主文件。

## 转换流程

1. 先清洗源测试点，只保留真实业务页面、功能区、控件规则和行为断言。
2. 将测试点拆成“一个可执行行为一个用例”的原子粒度；不要把整段页面规则堆成一个大用例。
3. 对新增、编辑、删除、关闭弹窗、表单校验、筛选、分页、状态切换、权限限制等行为分别拆用例。
4. 对 199/200/201 字、空字符串、空格、重复名称等边界值，优先整理成数据驱动用例，不要把一组边界值混成模糊描述。
5. 明确每条用例的前置条件、测试数据、操作步骤、预期结果、脚本分组建议和可自动化性。
6. 将无法直接落为 UI 脚本的场景单独标记，例如“需接口联合断言”“需数据库联合断言”“待确认已下线功能”。
7. 输出标准 Markdown 用例文件，并在最终回复中汇报用例数量、待确认项数量和推荐脚本拆分方案。

## 清洗规则

- 忽略资料型分支，例如“问题汇总”“其他”“备注”“需求说明”等非业务测试点分支。
- “页面规则”中的纯样例文案、示例名称、演示数据、说明性标题，不要逐行强行翻成独立用例。
- 只有当页面规则明确表达了界面行为、字段校验、弹窗标题、按钮动作、状态切换或显示规则时，才转换为自动化用例。
- 若项目知识沉淀已明确某功能在后续版本移除，而源测试点仍保留该功能，保留该用例但标记为“待确认”，不要静默删除。
- 若测试点只说“列表筛选正确”“字段展示正确”，必须结合同级字段说明拆成更具体的自动化用例；若字段说明缺失，则保留为待确认项。

## 输出规则

- 默认输出 Markdown 表格格式的 UI 自动化测试用例文件。
- 默认文件名使用 `<页面或模块><版本>_UI自动化测试用例.md`。
- 默认使用中文输出，保持 UTF-8 编码。
- 用例文件至少包含：基本信息、待确认项、用例明细、自动化脚本拆分建议。
- 若当前输入不足以支持脚本开发，必须把缺失项写进“待确认项”，而不是伪造页面 URL、角色矩阵、接口断言或测试数据。
- 若已有定位资产或 Page Object，可在备注中引用，但不要在本 Skill 内直接生成脚本代码。

## 自动化拆分建议规则

- 先按页面内的主功能区拆分脚本，例如：`smoke`、`manage`、`tag_group`、`permission`。
- 单页面初始脚本数量优先控制在 3 到 6 个文件，不要默认把每类动作都拆成独立文件。
- 只有当页面长期演进、功能复杂或多人并行维护时，才继续细拆为 `validation`、`submit`、`toggle`、`unbind` 等更细文件。

## 最终回复

至少汇报：

1. 来源测试点文件与转换范围。
2. 输出文件路径。
3. 生成的用例数量。
4. 待确认项和高风险项。
5. 推荐的自动化脚本拆分方案。
