# 测试点矩阵

使用本矩阵避免接口用例设计停留在“请求成功”层面。

## 正常场景

- 最小合法请求
- 全量合法请求
- 每个独立筛选或动作参数
- 每组并列筛选维度分别覆盖，例如业务日期筛选与更新时间筛选分别建场景
- 合法参数组合
- 预期有数据返回
- 预期空结果返回

## 边界场景

- 字符串最小/最大长度
- 数值最小/最大值和精度
- 时间开始/结束边界是否包含
- 时间跨度上限
- 仅开始值
- 仅结束值
- 枚举每个合法值
- pageNo/pageSize 最小值和最大值
- 批量数量上限
- 合法筛选条件下的空列表

## 异常场景

- 缺少必填参数
- 参数类型错误
- 参数格式错误
- 非法枚举值
- 超出范围
- null、空字符串、空白字符串
- 开始值大于结束值
- 两套并列筛选维度混用或冲突
- 不支持的参数组合
- JSON 格式错误或 Content-Type 不匹配

## 权限与安全

- 未传 token 或 token 非法
- token 过期
- 无资源权限
- 跨租户、跨店铺、跨账户访问
- 用户角色边界
- 接口存在签名时的签名错误、nonce 重放
- 响应和日志敏感信息脱敏

## 分页、排序、筛选

- pageNo/pageSize 基础查询
- pageSize 上限
- 首页、中间页、末页
- cursor 首次读取和续读
- cursor 续读携带首包同值参数
- cursor 续读携带与首包不一致参数
- cursor 与 page 参数同时传
- 跨页不重复、不漏数
- 重复请求排序稳定
- 分页过程中筛选条件持续生效

## 用例粒度门禁

矩阵中的每条用例都必须满足以下原则：

- 只覆盖一个主校验机制
- 只引入一个主变量变化
- 只产生一类主要失败归因
- 执行后能输出唯一结论
- 能被脚本和报告一对一追溯

出现以下情况时，必须拆分成多条用例：

- 用例标题中出现“、”“及”“或”等并列异常项
- 请求参数重点同时包含多个异常输入
- 预期结果可能对应多个错误码、多个错误文案或多个失败层级
- 需要多次不同请求才能完整覆盖
- 同时覆盖“参数缺失 + 参数非法 + 权限不足”这类不同机制
- 同时覆盖“鉴权失败 + 业务失败”两层失败

推荐拆分方式：

- 鉴权类按失败机制拆分
- 分页类按首包、续读、重复续读、参数不一致续读拆分
- 范围类按正常、仅开始、仅结束、开始大于结束、非法格式、超上限拆分
- 权限类按无权限应用、越权对象、失效对象、不存在对象拆分
- 兼容类按空串、null、空白串、未知参数分别拆分

正反例：

- 反例：`直连网关鉴权负向：缺 Header、错误签名、过期 timestamp、重复 nonce`
- 反例问题：命中多个不同校验机制，执行后无法唯一归因，报告无法一条映射一个失败原因
- 正例：`缺 X-Linker-AppId`、`缺 X-Linker-Timestamp`、`缺 X-Linker-Nonce`、`缺 X-Linker-Signature`、`X-Linker-Signature 错误`、`X-Linker-Timestamp 超时`、`X-Linker-Nonce 重放`

## 设计门禁

生成矩阵前后，必须检查以下问题：

- 是否先完成了参数语义分组，而不是直接照着 `requestExample` 写测试点
- 是否把名称相似但语义不同的参数拆成不同测试组，例如 `dateStart/dateEnd` 与 `updateTimeStart/updateTimeEnd`
- 是否为每一组独立筛选维度至少设计了一组正常场景，满足最小 `Each Choice`
- 是否为范围类参数补齐边界值分析，不只覆盖“合法示例”
- 是否为互斥、条件必填、cursor 参数一致性等规则补齐决策表或等价的合法/非法组合
- 是否为 `cursor`、分页 token 等状态参数补齐状态迁移，不只覆盖“续读成功”
- 是否把“分组名称”误当成“单条用例名称”
- 是否存在无法在执行报告中唯一映射到单一失败原因的用例；若存在，必须拆分

## 兼容性

- 老请求体不传新增参数
- 新参数不传
- 新参数单独传
- 新参数与旧筛选条件组合
- 老客户端仍传废弃参数
- 未知额外参数处理
- 默认值行为

## 数据正确性

- 返回记录符合请求筛选条件
- 业务唯一键能映射到源数据
- 金额精度和舍入
- 时区和时间格式
- 状态和枚举映射
- 主明细数量和关系一致
- 有条件时与数据库或下游数据一致
