# Verify JSON Order Ingestion

## 目标

核验已经执行完成的 JSON 订单解析入库结果。典型链路：

`source_table.source_json` -> 解析订单主信息 -> `adapter_standard_order` 或等价订单主表 -> 解析明细数组 -> `adapter_standard_order_detail` 或等价订单明细表。

默认只做只读核验。除非用户明确提出单独的数据写入/修复请求，否则不得执行解析任务、迁移任务、修复 SQL、清理 SQL 或任何会改变数据库状态的操作。

## 必须流程

1. 先收集核验事实，再产出结论：
   - 数据库类型、连接方式、只读账号信息；密码优先使用环境变量。
   - 源表、源主键、JSON 字段、源数据过滤条件。
   - 订单主表、主键、业务键、目标过滤条件。
   - 订单明细表、明细主键、关联订单主表的外键。
   - 明细数组 JSON Path。
   - 完整字段映射，或足以生成映射草稿的接口文档字段说明、数据库列注释/列名。
   - 明细匹配策略：优先使用稳定业务键，如 `sku_id`、`line_no`、`item_id`；没有稳定键时按配置顺序比对，并在报告中声明残余风险。
2. 如果缺少字段映射且用户提供接口文档，先执行“映射草稿流程”。如果既没有映射，也没有文档/表注释，先向用户确认，不能凭空核验字段。
3. 基于 `references/config-template.json` 在用户工作区创建或更新核验配置。真实密码、token、cookie、完整连接串不得写入配置产物或报告；使用 `DB_PASSWORD` 等环境变量承载密钥。
4. 先做小范围冒烟核验，再做全量核验：

```bash
python <skill_dir>/scripts/verify_json_order_ingestion.py --config <config.json> --limit <n> --output <report.md> --html-output <report.html> --diff-json <diff.json>
python <skill_dir>/scripts/verify_json_order_ingestion.py --config <config.json> --output <report.md> --html-output <report.html> --diff-json <diff.json>
```

5. 核验完成后必须审阅 Markdown 摘要、完整差异 JSON 和 HTML 报告，并按类型归类：
   - 源 JSON/源数据问题：无效 JSON、非对象 JSON、业务键缺失、源业务键重复。
   - 订单主表问题：主表缺失、主表重复、主表字段不一致、主表目标列缺失。
   - 订单明细问题：明细数组缺失/非数组、明细数量不一致、明细缺失/多余、明细字段不一致。
   - 主明细关系/幂等问题：孤儿明细、目标业务键重复、源/目标明细匹配键重复。
   - 映射缺口与平台适用性问题：目标业务字段未发现明确源 JSON 解析字段、平台文档未提供、字段是否适用待确认、用户/研发已确认关闭的字段口径。
6. HTML 报告是主要交付物，必须生成独立 `.html` 文件。Markdown 与 diff JSON 只是支撑产物，不能替代 HTML 报告。
7. 最终回复使用简体中文，除非用户明确要求其他语言。必须包含核验范围、核验行数、通过/不通过结论、TOP 差异、HTML 报告路径、支撑产物路径、阻断项或假设。

## HTML 报告结构

HTML 报告必须按“总览到明细”的顺序组织，便于先看结论再定位字段：

1. 核验总览：结论、源数据行数、有效 JSON 行数、已核验订单数、已核验明细数、差异总数、阻断项数量、生成时间。若源表或目标表是动态业务表，必须展示快照生成时间，并声明“本报告以当前只读事务快照为准”；同一范围多次重跑行数变化时，必须在限制或假设中说明动态数据影响。
2. 核验范围：数据库类型、源表/JSON 列、源过滤条件、订单主表、订单业务键、明细表、明细外键、明细数组路径、明细匹配键、字段映射数量、金额精度、时区。
3. 核验依据：列出接口文档、字段映射配置、数据库字段注释、用户/研发确认口径等依据。第三方平台 API 文档不得只贴 URL，必须写清平台、文档名称、接口名、URL、访问时间、适用 JSON 节点/字段范围，以及不覆盖的范围。
4. 总量与差异分布：按源数据、订单主表、订单明细、主明细关系/幂等、其他问题统计差异数；同时列出差异类型计数。
5. 目标表字段映射矩阵：必须以目标数据表字段为主视角，分别展示主表和明细表全部字段；每行至少包含“数据表字段、字段注释、预期 JSON 取值字段、实际清洗取值字段、预期推断依据、转换/比对规则、比对结果”。已核验字段写明通过/不通过和差异数；技术字段必须明确标注“技术字段，非 JSON 业务字段”。业务字段不得简单用“未纳入硬判”跳过：若 API 文档、表字段注释或源 JSON 已存在预期/候选来源，但目标字段未清洗、为空或未承载，必须标记为“待研发确认缺陷”或“映射确认项”，并进入缺陷/确认项清单；仅当源侧未发现稳定来源且无明确业务映射依据时，才可标注“暂不适用/平台未提供待确认”。
6. 暂不适用/平台未提供待确认字段汇总：凡映射矩阵中标注“暂不适用/平台未提供待确认”或“未发现明确源 JSON 解析字段”的目标字段，主报告必须单独成章汇总，字段以目标表字段全名展示。主报告面向结论阅读，只展示一个“目标实际入库值”列，明确写成全为 NULL、全为空串、全为 0、混合分布或全为非空业务值，并带范围行数与 DDL 默认值；不得在主报告中把 NULL 数、非空数、空串数、0 值数拆成多列造成阅读歧义。diff JSON 或复核明细附件必须保留范围行数、NULL 数、非空数、空串数、0 值数、DDL 默认值等拆分统计证据，不得只写“目标为空”。
7. 差异与观察项说明：严格差异不得直接等同于缺陷。凡差异可能来自空串、空白字符、大小写、格式化、NULL 表达、金额精度或时间归一规则，必须同时展示归一后差异数，并明确写清“有效业务值是否已承载”“是否属于缺陷”；归一后差异为 0 的观察项不得列入待研发确认缺陷。
8. JSON 字段视角映射（补充）：可保留 JSON path -> 目标字段的映射，用于辅助排查，但不能替代目标表字段矩阵。
9. 源 JSON/源数据问题：展示源 ID、订单键、差异类型、错误原因。
10. 订单主表问题：展示源 ID、订单键、字段、期望值、实际值、差异类型。
11. 订单明细问题：展示源 ID、订单键、明细键、字段、期望值、实际值、差异类型。
12. 主明细关系/幂等问题：展示孤儿明细、重复订单、重复明细键等问题。
13. 阻断项与假设：列出导致无法继续判断的配置/数据问题，以及用户确认过的核验假设。
14. 差异样本明细：展示受 `--max-report-diffs` 控制的差异样本；完整差异以 `--diff-json` 为准。
15. 待研发确认缺陷、映射确认项与关闭记录：列出所有“有预期/候选来源但目标未承载”的业务字段，至少包含编号、类型、字段、证据、当前表现、建议处理；不得把此类字段放在通过结论里关闭。用户或研发已确认关闭的字段必须保留关闭原因、证据和后续重新打开条件，但不得继续计入缺陷数或待确认项数量。
16. 产物路径：列出 HTML、Markdown、diff JSON 的绝对路径。主报告只展示结论、摘要、关键统计和关键风险；SQL 复核明细、字段拆分统计、差异样本全集和空值归一样例应输出为复核明细附件或 diff JSON，避免主报告堆砌执行流水。

报告必须是中文、可离线打开、不得依赖外部 CDN、不得包含真实密码/token/cookie/完整连接串。展示值要做 HTML 转义，长字段可截断；敏感字段必须脱敏或不输出。

## 映射草稿流程

当用户提供接口文档但没有完整 JSON 到表字段映射时，先生成映射草稿，再核验。

1. 提取接口字段清单：
   - OpenAPI/Swagger JSON/YAML：读取响应 schema 字段与 description。
   - Markdown/TXT：优先解析包含字段名、路径、描述/注释的表格。
   - PDF/DOCX/HTML 或不规则文档：手工整理成 `references/api-fields-template.json` 结构后再执行脚本。
2. 提取目标表列：
   - 优先读取 `information_schema.columns` 的列注释。
   - 列注释为空时，使用列名作为辅助匹配文本。
   - 没有数据库连接时，整理成 `references/table-columns-template.json`。
3. 执行映射生成：

```bash
python <skill_dir>/scripts/generate_mapping_draft.py --api-doc <api_doc.md|json|yaml> --db-config <config.json> --output-config <mapping_config.json> --output-report <mapping_report.md>
```

离线模式：

```bash
python <skill_dir>/scripts/generate_mapping_draft.py --api-fields-json <api-fields.json> --columns-json <columns.json> --detail-array-path "$.details" --output-config <mapping_config.json> --output-report <mapping_report.md>
```

4. 使用映射草稿前必须评审：
   - `score >= 0.75`：字段含义明确时可采用。
   - `0.55 <= score < 0.75`：必须请用户确认。
   - 未匹配、低置信、冲突匹配：不得作为最终核验映射，除非用户确认。
5. 只能把已确认的映射写入最终核验配置，再执行入库结果核验。

不得把自动匹配结果描述成事实。必须说明匹配依据：`comment match`、`field-name match`、`type-assisted match` 或 `manual review required`。

## 核验规则

- 以源 JSON 作为基线，除非用户明确指定其他权威来源。
- 订单主表按业务键比对，不按自增 ID 直接比对。
- 明细优先按稳定业务键匹配；没有稳定键时按配置排序比对，并声明风险。
- 金额/小数按配置精度归一化，常见金额字段默认 `scale=2`。
- 时间字段按配置格式和时区归一化。
- 核验顺序固定为：总量统计 -> 源 JSON 合法性 -> 订单业务键 -> 主表存在性/唯一性 -> 主表字段 -> 明细数量 -> 明细匹配 -> 明细字段 -> 主明细关系/幂等。
- 无效 JSON、必填 JSON Path 缺失、目标列缺失、字段归一化失败，均视为阻断项。
- SQL 必须只读。内置脚本只生成 `SELECT`，并拒绝包含分号或写操作关键字的 SQL 片段。
- 生成映射时优先使用接口字段注释与数据库列注释的语义匹配；仅在注释缺失时使用字段名匹配。
- 不要自动映射主键、明细外键、纯技术字段，除非用户明确标记为业务核验字段。

## 配置补充

可在配置中增加 `report` 节点，用于补充 HTML 报告中的人工说明：

```json
{
  "report": {
    "title": "JSON订单入库核验报告",
    "assumptions": ["明细无稳定业务键，已按目标表 id 排序比对"],
    "blockers": []
  }
}
```

## 资源

- `scripts/verify_json_order_ingestion.py`：只读核验脚本，支持 MySQL、PostgreSQL、SQLite；解析源 JSON，核对订单主表/明细表，并输出 Markdown、完整 diff JSON、中文 HTML 报告。
- `scripts/generate_mapping_draft.py`：接口文档字段与数据库列注释/列名匹配脚本，生成候选核验配置与 Markdown 映射评审报告。
- `references/config-template.json`：核验配置模板，包含源表、目标主表、目标明细表、字段映射、归一化规则与可选检查项。
- `references/api-fields-template.json`：接口字段离线整理模板。
- `references/table-columns-template.json`：数据库列离线整理模板。
