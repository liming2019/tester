# 功能测试用例评审检查清单

## 范围与来源

- 是否写明项目、版本、页面、模块和来源材料。
- 是否只覆盖当前需求或用户指定范围，没有扩展无依据功能。
- 经验补充是否标注为“测试补充”或“待确认”。

## 覆盖完整性

- 正常场景是否覆盖主路径。
- 边界场景是否覆盖长度、金额、数量、日期、分页、枚举和阈值。
- 异常场景是否覆盖必填、格式、重复、非法状态、依赖失败和重复提交。
- 权限场景是否覆盖入口、按钮、数据范围、越权访问和角色差异。
- 兼容场景是否覆盖浏览器、分辨率、历史数据、旧链接和不同账号类型。
- 数据一致性场景是否覆盖页面、接口、数据库、报表、日志或下游系统。
- 回归场景是否覆盖关联模块、存量数据和历史缺陷高发点。

## 用例质量

- 每条用例是否包含非空测试标题。
- 测试标题是否能单独表达主验证目标，而不是只写模块名、功能点名、场景类型或“校验正确”。
- 一条用例是否只有一个主验证目标。
- 前置条件、测试数据、步骤、预期结果是否齐全。
- 预期结果是否可观察、可断言、可复核。
- 是否存在“功能正常”“正确处理”“符合规则”等空泛预期。
- 多条件组合是否拆成判定表或等价的原子用例。
- 状态流转是否覆盖合法流转、非法流转和边界状态。

## 执行可用性

- 用例是否能被测试人员直接执行。
- 缺少账号、权限、测试数据、环境或接口联调时，是否明确标为待确认或阻塞。
- 数据修改类用例是否说明清理或回滚要求。
- 涉及敏感数据时，是否使用占位符或脱敏值。

## 后续衔接

- 适合 UI 自动化的用例是否标记为可自动化。
- 需要接口契约覆盖的内容是否移交 `api-test-design`。
- 需要页面定位和脚本生成的内容是否能继续交给 UI 自动化链路。
