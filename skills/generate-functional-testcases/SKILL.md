# 生成功能测试用例

使用本 Skill 时，只负责把需求事实、测试对象分析结果或功能测试点整理成可评审、可执行的普通功能测试用例，不负责重新提取蓝湖需求、生成接口矩阵、生成 UI 自动化用例或编写自动化脚本。

## 适用输入

可接收以下任一输入：

1. `extract-functional-test-points` 输出的 `plaintext` 测试点。
2. XMind 降级 Markdown、页面功能树或版本测试点清单。
3. `test-object-analysis` 输出的下游测试点生成输入、对象状态与规则矩阵、权限边界清单。
4. PRD、原型摘要、截图说明、变更说明或蓝湖结构化需求。
5. 已有功能用例，需要补齐、去重、拆分、重排优先级或补覆盖矩阵。

如果输入仍是蓝湖链接或未提取的蓝湖页面，先调用 `lanhu-to-testcase`。如果输入是接口文档或接口参数变更，使用 `api-test-design`。如果目标是 UI 自动化用例，使用 `generate-ui-automation-testcases`。

## 输入门禁

开始生成用例前，先确认以下信息：

1. 测试范围：项目、版本、页面、模块或变更点。
2. 来源依据：需求、原型、测试点、对象分析结果或用户补充。
3. 角色与权限：至少明确默认测试角色；不明确时列入待确认项。
4. 前置数据：账号、状态、已有记录、关联数据、开关配置或环境限制。
5. 验收标准：材料明确的结果、状态、字段、提示、数据变化或跳转。
6. 输出位置：默认写入项目 `testcases` 目录。

缺少关键信息时，不要脑补。可继续生成材料支持的用例，同时把缺口写入“待确认项”和用例备注。

## 何时读取参考

开始输出最终用例文件前，读取：

- `references/functional-testcase-template.md`：确认表头、章节和示例写法。

交付前自检时，读取：

- `references/testcase-review-checklist.md`：确认覆盖、粒度、来源依据和可执行性。

不要把 reference 全文复制进最终产物，只按任务需要使用其中规则。

## 生成流程

1. 归一化输入：识别页面、模块、功能点、入口、字段、状态、权限、数据关系和明确规则。
2. 建立覆盖矩阵：按正常、边界、异常、权限、兼容、数据一致性、回归影响归类。
3. 选择设计技术：
   - 字段输入、长度、金额、数量、日期：使用等价类和边界值。
   - 多条件组合、开关、角色、状态与字段联动：使用判定表。
   - 审核、启停、冻结、流转、回退、重试：使用状态迁移。
   - 跨页面流程、上下游链路、异步结果：使用场景法。
   - 多角色入口、按钮、接口鉴权差异：使用权限矩阵。
4. 拆分用例粒度：一条用例只验证一个主目标；多个独立失败原因必须拆分。
5. 补齐用例字段：编号、模块、功能点、场景类型、优先级、前置条件、测试数据、操作步骤、预期结果、来源依据、是否可自动化、备注。
6. 标记不可执行项：前置数据缺失、权限账号缺失、依赖接口未联调、环境限制、规则待确认的用例不得伪装成可执行 PASS。
7. 输出 Markdown 用例文件；用户明确要求 Excel 时，再另行生成 Excel。
8. 交付前读取最终产物自审，确认无乱码、无空泛预期、无敏感信息、无未解释的覆盖缺口。

## 输出规则

默认输出 Markdown 表格。文件名建议：

- 单页面：`<页面名>功能测试用例.md`
- 版本范围：`<版本号>功能测试用例.md`
- 模块范围：`<模块名>功能测试用例.md`

用例编号建议：

- 功能用例：`FT-模块缩写-001`
- 权限用例：`FT-AUTH-001`
- 数据一致性用例：`FT-DATA-001`
- 回归用例：`FT-REG-001`

优先级使用 `P0/P1/P2/P3`。场景类型固定使用：`正常`、`边界`、`异常`、`权限`、`兼容`、`数据一致性`、`回归`、`待确认`。

## 质量门禁

输出前必须满足：

1. 每条用例有明确来源依据；经验补充必须标注为“测试补充”或“待确认”。
2. 每条用例的步骤可执行，预期结果可观察或可核验。
3. 不输出“功能正常”“保存成功即可”“系统正确处理”等空泛预期。
4. 字段校验必须说明输入值、触发动作和预期提示或数据变化。
5. 权限用例必须说明角色、入口可见性、按钮可用性或越权访问预期。
6. 数据一致性用例必须说明核验对象，例如页面、接口、数据库、报表、日志或下游系统。
7. 当前环境无法执行的用例保留，但标记 `BLOCKED`、`待确认` 或写明前置缺口。
8. 不把接口契约测试矩阵、UI 自动化脚本步骤、数据库迁移报告混入普通功能用例。

## 与其他 Skill 的衔接

- 蓝湖输入：先 `lanhu-to-testcase`。
- 复杂业务：先 `test-object-analysis`。
- 测试点提取：先 `extract-functional-test-points`。
- 普通功能测试用例：调用本 Skill。
- UI 自动化用例：调用 `generate-ui-automation-testcases`。
- Playwright 脚本：调用 `generate-playwright-from-ui-testcases`。
- 接口测试用例或矩阵：调用 `api-test-design`。

## 最终回复

至少包含：

1. 输入来源和测试范围。
2. 输出用例文件路径。
3. 用例总数和各场景类型数量。
4. P0/P1 用例数量。
5. 待确认项、不可执行项和主要风险。
6. 是否建议继续转 UI 自动化用例或接口矩阵。
