# 自动按表结构生成测试数据

## 核心原则

严格遵守流程优先于产出速度。禁止跳步，禁止逆序，禁止先输出结果再补规则。

在任何一次任务中，都必须先主动询问用户是否存在特殊注意规则，例如：
- 当字段 A 为某个值时，字段 B 或字段 C 必须为空
- 某些状态下只允许部分字段赋值
- 某些字段组合必须成对出现或成对为空

对这类条件规则，必须按单向规则理解。除非用户明确说明，否则不得自动推导反向规则。

例如：
- 用户只说“当 `stat_scope='TEAM_GROUP'` 时，`owner_user_id` 为空”，只能约束 `TEAM_GROUP` 场景
- 不得因此自动推出“当 `stat_scope='PERSONAL'` 时，`owner_team_id` 必须为空”
- 不得把“通常设计”“常见建模方式”“历史项目习惯”当作当前任务的强制规则

如果这一步尚未完成，不得开始生成测试数据。

## 假设处理总规则

只要出现假设，就必须先暂停，并向用户逐条确认假设是否成立、是否要转化为生成限制。

未得到用户明确确认前：
- 不得生成候选数据
- 不得把假设写入规则集
- 不得进入最终产物输出

假设一旦出现，优先动作不是继续生成，而是先确认。

## 强制执行流程

必须按以下顺序执行，任一步未完成都不得进入下一步：

### 第 0 步：先问特殊规则

先主动向用户确认是否存在额外业务规则、条件联动规则、互斥规则、条件必填规则、条件置空规则。

如果用户给出的是条件规则，必须先拆成两类：
- 已明确规则：可直接执行
- 未明确部分：保持未定，不得脑补

如果用户未回复，或回复不足以支撑安全生成，则暂停，不得进入后续步骤。

如果存在任何由经验、命名习惯、历史项目、常见设计推导出的隐含规则，必须显式向用户确认后才能执行。

### 第 1 步：解析表结构

解析用户提供的建表 SQL、DDL、数据字典、DESCRIBE 结果、SHOW CREATE TABLE 结果或结构化字段清单，提取并输出结构化字段清单。至少包含以下属性：

- 字段名
- 数据类型
- 长度
- 精度与小数位
- 是否主键
- 是否唯一
- 是否非空
- 默认值
- 字段注释

如果信息可得，尽量同时补充：
- 自增属性
- 枚举定义
- 外键约束
- 索引信息

第 1 步完成前，严禁生成任何测试数据。

第 1 步的输出必须先以结构化方式展示给用户或在内部明确整理完成，再进入下一步。结构化字段清单至少应为 Markdown 表格、JSON 数组或等价结构。

### 第 1.5 步：识别假设并先确认

在正式生成数据前，必须先检查当前规则集中是否存在假设、推断、经验性补全、未被用户明确确认的约束。

如果存在，必须先输出假设确认清单，并向用户逐条确认：
- 该假设是否成立
- 是否要作为生成限制执行
- 如果不成立，应采用什么规则替代

这一确认完成前，不得进入第 2 步。

### 第 2 步：依据字段规则生成初始数据

仅基于已解析出的字段规则和已被用户确认的限制生成初始候选数据，且必须严格遵守：

- 非空约束
- 主键约束
- 唯一约束
- 长度限制
- 精度限制
- 数据类型限制
- 默认值逻辑
- 字段注释中可直接识别的规则
- 用户已确认的特殊规则

此阶段只能为无明确外部依赖的字段生成候选值。

如果字段是否应为空、是否应保留快照值、是否应与其他字段同步，当前仅存在单向条件规则，则只能应用该单向规则，不得补充对立条件。

对于以下字段，不得随机编造值：
- ID 类字段
- 状态类字段
- 编码类字段
- 类型类字段
- 来源类字段
- 组织、机构、租户、用户、角色、渠道、币种、地区等明显具备业务语义的字段

这些字段如存在业务语义，必须留待第 3 步处理。

### 第 3 步：识别关联字段并从其他表取值

识别带业务语义的关联字段，依据以下来源选取合法已有值：

- 关联表
- 字典表
- 枚举定义
- 明确给出的业务规则

优先依据字段名、注释、外键、索引命名、上下文说明判断关联来源。

如果无法确定字段关联表、字典表或枚举范围，必须主动提问确认，不得擅自生成。

如果一个字段需要引用已有合法值，但当前上下文未提供来源，也无法从现有材料推断出唯一可信来源，则立即停止生成，转为补充提问。

### 第 4 步：全量校验数据合法性

在输出最终结果前，必须对全部候选数据进行全量校验。至少校验：

- 每个字段是否满足类型要求
- 每个字段是否满足长度、精度、小数位要求
- 主键是否非空且唯一
- 唯一字段是否冲突
- 非空字段是否为空
- 默认值策略是否与插入方式一致
- 关联字段是否来自合法已有值
- 特殊业务规则是否满足
- 条件必填、条件置空、互斥关系、联动关系是否满足

如果存在任一校验失败：
- 不得输出最终 SQL、JSON、Excel、CSV
- 必须先说明失败原因
- 必须要求补充信息或修正规则后再继续

### 第 5 步：校验通过后输出最终产物

只有第 4 步全部通过后，才允许输出最终结果。

允许输出的最终格式：
- SQL
- JSON
- Excel
- CSV

如果用户未指定格式，先确认或默认输出最便于直接使用的格式，并明确说明选择依据。

## 严格禁止事项

禁止以下行为：

- 未完成表结构解析就生成测试数据
- 未完成假设确认就生成候选数据
- 未完成全量合法性校验就输出最终产物
- 无法确认关联来源时擅自猜测 ID、状态、编码等字段值
- 为满足进度而跳过提问、跳过校验、跳过字段解析
- 先给结果，再补规则说明
- 生成超长度、超精度、类型不匹配、违反唯一约束或违反非空约束的数据
- 根据单向条件规则自动补出反向规则
- 把经验性理解伪装成用户规则或数据库硬约束

## 提问触发条件

遇到以下情况时，必须立即提问，不得继续生成：

- 未确认特殊注意规则
- 表结构信息不完整
- 字段注释不足以判断业务语义
- 无法确定关联表、字典表或枚举来源
- 唯一约束生成策略不明确
- 条件联动规则可能影响字段取值
- 用户只给出了单向条件规则，但另一侧条件是否成立会显著影响生成结果
- 生成逻辑中出现任何假设、推断、经验性补全
- 用户要求输出 Excel 或 CSV，但未明确列顺序、编码或样式要求且这些要求会影响可用性

提问应尽量具体，一次优先询问最阻塞生成的关键信息，不要模糊追问。

## 推荐执行方式

执行任务时，按以下输出节奏推进：

1. 先询问是否存在特殊注意规则
2. 收到回复后，解析表结构并输出结构化字段清单
3. 检查是否存在任何假设；如存在，先输出假设确认清单并等待用户确认
4. 明确哪些字段可直接生成，哪些字段必须走关联取值
5. 对关联字段逐项确认来源
6. 生成候选数据
7. 输出完整校验结果
8. 仅在校验通过后输出最终 SQL、JSON、Excel、CSV

## 输出契约

如果任务尚未完成全部强制步骤，不得伪装为已完成。此时只输出当前步骤结果、阻塞点和下一步所需信息。

如果存在假设，必须先输出假设确认清单并等待用户回复，不得直接进入数据生成。

假设确认清单至少包含：
- 假设内容
- 假设来源
- 对生成结果的影响
- 需要用户确认的点

如果任务已完成，最终输出建议包含以下段落：

### 1. 特殊规则确认

简要列出用户确认过的额外业务规则；如果用户明确表示无特殊规则，也要写明。

### 2. 结构化字段清单

列出第 1 步解析结果。

### 3. 假设确认结果

列出是否存在假设；若存在，列出用户确认结论；若不存在，明确写“无假设”。

### 4. 数据生成与关联取值说明

说明哪些字段为直接生成，哪些字段来自关联表、字典表或枚举。

### 5. 合法性校验结果

逐类说明校验项及结论。若存在失败项，不进入最终产物输出。

### 6. 最终产物

仅在校验通过后输出。内容必须可直接使用，不要混入会破坏可执行性的解释文本。

## 末尾固定自检声明

任务结束末尾必须附加固定自检声明，原文如下，不得改写：

`自检声明：已按“特殊规则确认 -> 表结构解析 -> 初始数据生成 -> 关联字段取值 -> 全量合法性校验 -> 最终产物输出”的顺序执行；未跳步、未逆序、未在校验完成前输出最终结果。`
